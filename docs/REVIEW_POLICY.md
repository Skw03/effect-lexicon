# 独立审查与修复复验规则

本规则适用于 Effect Lexicon 整个项目生命周期，执行范围始终受当次明确授权限制。依据：[原始要求](REQUIREMENTS_SOURCE.md) A–H（尤其 G3、H6）、[产品规范](SPEC.md)、[阶段路线](ROADMAP.md)、[代理规则](../AGENTS.md)及已明确批准的修订。当前授权止于 Stage 5；本文件不启动任何后续阶段或部署。

## 要求、阶段与批准

- 原始要求是保留不改的来源档案；SPEC 是落实已批准修订的产品规范，ROADMAP 定义阶段顺序，AGENTS 定义执行规则。对同一事项，最新明确批准的修订优先于被取代的旧要求；记录批准来源、适用条款与边界，不把建议、实现日志或测试通过当成豁免。
- 先判定要求性质（mandatory / recommended / conditional）、当前阶段及触发条件，再检查实现。原文中尚未获授权的未来提示词不是执行指令；未到期要求记 NOT DUE，不能提前实现，也不能因尚未实现而判当前阶段 FAIL。
- 已明确批准的 Stage 1 界面方向、Stage 2–5 顺序推进与审查通过后协调合并继续有效。不恢复旧的逐阶段人工确认或人工专属合并规则。dots/SUN 在独立验收和必需检查通过、仓库权限允许后可协调阶段 PR/合并与下一阶段；工作者仍按具体 handoff 执行提交/推送，不直接写 main。
- 常规范围内的合规修复不重复索取产品批准。未解决的规范冲突、产品目标/重大视觉变化、技术栈/schema/依赖变化和权限问题，记录精确条款、影响和最小待决事项后交协调方集中升级；只暂停受影响动作，继续独立且已获授权的工作。不得降低测试、绕过权限或以换出口规避拒绝。
- Stage 5 完成后停止。Stage 6+ 需新授权，生产还需用户单独明确放行；Stage 6 授权本身不等于生产授权。原文 H2 合并触发生产与禁止 agent 生产部署的冲突须在该未来阶段先解决；合并不得意外触发部署。本规则不配置流水线、宿主、域名、生产触发或发布 tag。

## 职责与独立性

- 实施者负责实现、复现、修复与自检，交付精确候选和证据，不为自己的实现签发独立 PASS 或关闭缺陷。
- 独立审查员必须未参与受审实现，使用新会话或隔离审查上下文；亲自读实际 diff、规范和代码，在指定环境的干净隔离 checkout 实跑适用检查。实施者日志仅作为线索，不代替审查证据。审查模式不改产品；若审查员接手修复，该修复须换另一独立审查员复验。
- 协调方负责当前授权、范围、分派、冲突升级、整合候选及阶段门，不把转述或自审冒称独立实测。原实施任务不可用时可明确指定继任者，并保留模块责任和交接链。
- 审查职责是可交接角色，不依赖某个永久运行的代理或任务。后备审查员从仓库中的规则、当前 PROGRESS、历史报告、矩阵及新修复提交恢复上下文，核验基底和未关闭项后接手；无法取得的证据标明缺口并复跑必要部分。

## 生命周期检查点与覆盖

1. 接手或开始任务：核实 origin、远端 main、工作树、任务分支、精确基底与授权，保留并发修改；读取 AGENTS、ROADMAP、最近五条 PROGRESS 及受影响规范/审查记录。
2. 每阶段候选完成后：独立 H6 检查该阶段所有适用完成条件和继承功能。Stage 5 按 SPEC §11 的 13 项逐条检查，覆盖 18 效果；真实运行、交互/视觉及自动审计互补，不能用通过的旧脚本排除未覆盖的真实缺陷。
3. 缺陷修复提交后：在精确修复 SHA 上独立重现原步骤、验证完整验收条件及受影响回归；特别检查交互混用、边界参数、减少动态与清理。仅提交实现者自检报告不能关闭。
4. 多分支整合或准备合并时：核对已复验的修复 SHA、整合实际 diff、冲突解决与最终候选 SHA；对相互影响的部分复验。单分支通过不自动覆盖整合后的组合。未解决的必需 FAIL 不得以“准备就绪”推进。
5. 后续获授权的发布、内容波或实质需求/架构变化：按对应阶段门进行独立审查；发布前的人类内容终审、独立预览和生产批准不得被替代。未来检查点只是规则，当前不执行 Stage 6+。

检查范围随变化与证据确定。未变工作可引用绑定精确旧 SHA 的独立证据，列出文件等价或不受影响的理由；不反复全审全部历史。受影响代码、共享依赖、运行环境或验收条件变化时扩大复验，必要时重跑全套。AGENTS 的 typecheck、lint、test、build 质量门仍执行；文档治理更新检查引用、差异与授权边界，不把这些检查称为产品 H6。既有断言不得删除、跳过或弱化。

## 条目状态与总体结论

要求矩阵使用且只使用以下五种条目状态；保留稳定 ID、来源、性质、阶段、证据与限制：

| 状态 | 含义 |
| --- | --- |
| PASS | 已独立验证所列要求及范围；不外推到未测设备、状态或版本。 |
| FAIL | 在当前适用范围内已复现违反要求，关联稳定缺陷 ID 和验收条件。 |
| BLOCKED | 验证缺少具体工具、设备、权限或必要信息；写明已做部分、缺口和恢复条件，不虚构产品失败或测试通过。 |
| NOT DUE | 尚未到期或未授权的未来阶段要求，注明阶段门；不是当前缺陷。 |
| NOT APPLICABLE | 该要求的明确条件不适用，给出来源与理由；不能用于逃避当前义务。 |

总体 verdict 使用三种，与原文 H6 对应：

| Verdict | H6 对应 | 判定 |
| --- | --- | --- |
| PASS | ready to merge | 当前范围的必需验收已满足，无未解决必需 FAIL；披露可选建议与非阻断覆盖限制。仅表示审查就绪，不授予合并或部署权限。 |
| CHANGES REQUIRED | ready after fixes | 有已确认需修复的偏差；即使自动门全绿仍不可按 PASS 推进。修复并独立复验前保持此结论。 |
| BLOCKED | not ready | 关键证据、授权或条件缺失，不能形成完整通过判断；写明恢复审查所需条件。 |

已确认 FAIL 与覆盖 BLOCKED 可以并存。存在已确认缺陷时总体至少 CHANGES REQUIRED；如关键阻塞使判断无法完成，报告 BLOCKED 并保留全部已确认 FAIL。非必需真实设备覆盖缺失不自动等于产品 FAIL，但也不得表述为已验证。OPTIONAL/P3 是建议或严重性标注，不增加第六种条目状态；不擅自把建议升级成硬要求。严重性与状态分开：当前 P2 只要违反必需条件仍阻止验收，不因没有 P0/P1 而放行。

## 证据与缺陷关闭

每份独立报告至少记录：仓库、基底与受审完整 commit SHA、审查日期/独立角色、适用阶段和批准依据、实际 diff/范围、每项状态、文件行号（属于该 SHA）、复现步骤、期望/实际、运行命令和退出结果、工具版本、访问地址类型、指标、覆盖限制、总体 verdict 和下一步。未提交候选还须记录完整 patch SHA-256、字节数和应用基底；不能以可变分支名代替版本。提交后核对与候选等价，关闭缺陷必须有提交后的独立复验。

- 缺陷记录保留稳定 ID、严重性、来源要求、受影响阶段/模块、实施责任角色、发现版本、复现证据、修复验收条件、修复 SHA、独立复验 SHA/证据和当前 OPEN/CLOSED。OPEN/CLOSED 是缺陷生命周期，不替代上述五种要求状态。
- 修复提交后，在独立复验完成前仍为 OPEN（可注明“已提交待复验”）。只有独立审查员在该提交验证原缺陷消失、完整验收条件通过、相关回归无倒退，才在新的复验记录中判定 CLOSED，并关联要求的新状态。失败或证据不足继续 OPEN；复发沿原 ID 重开并记录新 SHA。
- 复验不能只跑作者新加的测试；先核查根因修复和断言是否覆盖原步骤，再补充独立探针。真实 Lighthouse/axe 必须用真实工具数据，注明版本、页面和类别；SVG/动态颜色、混合输入等自动工具盲区须补运行证据。不能以分数或零严重违规替代具体要求。
- 原始失败记录和历史 verdict 保留，不把旧报告改成新版本 PASS。新复验单独记录，PROGRESS 指向当前快照；矩阵的新版本须带新 SHA 和证据，不能无依据改绿。公开记录只保留项目技术摘要与可复跑入口，原始日志/截图/附件的保存或外发遵守单独授权，不附秘密或个人数据。
